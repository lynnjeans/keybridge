From a request to a release

How work on SameKeys moves from an idea to an update on every installed copy, as done for 1.1, 1.2 and 1.3. Each change is one ticket; a release gathers whatever is merged.

Maintainer decides or does it by hand Claude Code does it, then reports

1. One ticket, from request to merge

Repeated for every change. Numbers count up: SK- followed by the next free number.

  1. Request Maintainer

    A feature, a fix, or feedback on something already built, such as “the rule editor is too wide”.

  2. Proposal Claude Code

    The options and a recommendation. Choices that belong to the maintainer, such as where an option lives in the UI, which email address to publish, or whether something becomes a preset, are asked before any code is written.

  3. Go-ahead Maintainer
  4. Ticket Claude Code

    A GitHub issue titled SK-xxx … with an estimate, a description and an acceptance checklist.

  5. Branch and build Claude Code

    On sk-xxx-short-name, everything the change touches goes in together:

    • code and unit tests
    • new strings in all ten languages (scripts/sync-strings.sh, no stale or untranslated entries)
    • the website, docs/ and the release checklist where they describe the change
    • project.yml, then xcodegen generate, when files move
  6. Verify Claude Code
    • The full test suite.
    • A signed test build, versioned like 1.2-sk280 (ALLOW_DIRTY=1 scripts/release.sh), installed in /Applications so permissions and settings carry over.
    • Checks on the real app: keys sent through System Events, screenshots of the windows involved, the app's log.
    • The Debug build is deleted afterwards, so Spotlight cannot start a second copy.
  7. Hand check Maintainer

    What a script cannot reach: a real key on a real keyboard (a Shift tap cannot be sent from the shell), pages behind a GitHub sign-in, mail arriving in an inbox.

  8. Commit and pull request Claude Code

    The commit says what changed and why; the pull request says what was checked and how. Done items in the issue are ticked.

  9. Merge Maintainer says so, Claude Code merges

    Squash merge into main (the repository allows no merge commits). The issue closes and the branch is deleted.

2. A release

Whenever the maintainer asks for one. Releases are numbered 1.1, 1.2, 1.3…; the build number only ever goes up by one.

  1. “Release it” Maintainer
  2. Version Claude Code

    A release ticket, then MARKETING_VERSION and CURRENT_PROJECT_VERSION raised in project.yml and the Xcode project.

  3. Release notes Claude Code

    release-notes/<version>/ in English, Simplified Chinese and Japanese: one short line per area, no introduction, checked against the defaults rather than the maintainer's own settings. They appear in the update window and on the GitHub release.

  4. Notes approved Maintainer

    The Chinese version is shown for review; nothing is built until it is approved.

  5. Merge and build Claude Code

    The version pull request is merged, then on a clean main:

    NOTARY_PROFILE=keybridge-notary scripts/release.sh

    A Release build, signed with Developer ID, the app and the DMG each notarized and stapled. Then stapler validate and spctl confirm Gatekeeper accepts it.

  6. Publish Maintainer

    In the maintainer's own terminal: scripts/publish-release.sh. It shows what is about to go out and waits for y, typed by hand. It uploads the DMG to a GitHub release and adds the version to site/appcast.xml, the feed every installed copy checks.

  7. Homebrew and checks Claude Code
    • scripts/update-cask.sh points lynnjeans/tap/samekeys at the new DMG.
    • The live feed on samekeys.com and brew info both show the new version.
    • On the maintainer's Mac, Check for Updates installs it; then the installed version, the process start time, both permissions, the rules loaded and the event tap are confirmed from the log.
    • The release ticket is ticked and closed.
Skipped lately. releasing.md asks for a full pass of release-checklist.md on the release build before every release. 1.1, 1.2 and 1.3 went out without one; each change was checked on its own instead.

Ground rules

What holds at every step.

RuleWhy
Merging, publishing and changing the maintainer's settings wait for a yes. They are hard to take back, and a release reaches every installed copy.
The y at publishing is typed by the maintainer, never scripted. That prompt is the last look at what is about to ship.
Everything in the repository is in English; the app ships in ten languages. An international project; see README.md.
Test builds carry the ticket in their version, such as 1.3-sk282, and a build number no higher than the release. Easy to tell apart in a log, and Check for Updates still offers the next release.
Contact addresses are on samekeys.com, never personal. Forwarding can change without a release.
